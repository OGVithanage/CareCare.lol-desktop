# Per-website subdomain UI and backend integration plan

Date: 2026-09-12

Status: Proposed UI integration for the implemented version 2 allowlist and Windows hostname enforcement.

## Goal

Finish the per-website subdomain feature through the existing Electron interface. Keep the current add-form toggle and visual direction. Each saved website row gains a compact icon control that:

- clearly shows whether additional subdomains are allowed;
- lets the user change that website's setting;
- saves and applies the full version 2 policy immediately;
- remains understandable to keyboard and screen-reader users.

The main domain and its conventional `www` alias remain allowed in either state. The setting controls other descendants such as `mail.example.com` and `a.mail.example.com`.

## Current state

The add form already contains a styled `#allow-subdomains` checkbox. It is not read by `src/renderer.js`.

The renderer still models websites as URL strings:

```js
[
  "https://example.com"
]
```

The main process already stores and returns the required version 2 representation:

```js
{
  version: 2,
  websites: [
    { domain: "example.com", allowSubdomains: true }
  ]
}
```

For compatibility with the unchanged renderer, `src/main.js` currently returns both `result.websites` and `result.allowlist`, and accepts either legacy strings or a version 2 payload. This compatibility preserved settings during the enforcement implementation, but the UI should now use `result.allowlist` and send rule objects directly.

## Proposed row design

Keep the domain label and Remove action. Add an icon button immediately before Remove:

```text
https://example.com                    [subdomain icon]  Remove
```

Use a small hierarchy icon: one parent node connected to two child nodes. This communicates descendants more directly than a globe, link, or generic settings icon.

The icon is also the editing control:

- Off: outlined/muted nodes with a diagonal break or visibly disconnected children.
- On: solid connected nodes in the existing white foreground.
- Hover/focus: full opacity and the existing white focus outline.
- Saving: disabled appearance and no interaction.

Do not communicate state through color alone. The connected/disconnected shape, `aria-pressed`, accessible label, and tooltip all communicate it.

Recommended button markup generated by the renderer:

```html
<button
  type="button"
  class="subdomain-button"
  aria-pressed="true"
  aria-label="Additional subdomains for example.com: allowed"
>
  <!-- inline hierarchy SVG, aria-hidden="true" -->
  <span class="row-tooltip" role="tooltip">Additional subdomains allowed</span>
</button>
```

Use inline SVG or a CSS-drawn icon. Do not add an external image dependency. The current Content Security Policy has `img-src 'none'`, and a local inline control is simpler to package and recolor. The SVG must be decorative with `aria-hidden="true"`; the button supplies the accessible name.

Use `aria-pressed` because the icon is a two-state button. Update the label with the state:

```text
Additional subdomains for example.com: allowed
Additional subdomains for example.com: blocked
```

The tooltip should say `Additional subdomains allowed` or `Additional subdomains blocked`. The word “additional” avoids implying that `www` changes with the control.

The row button should have at least a 36 by 36 pixel hit area even if the icon is 16–18 pixels. At narrow widths, keep the domain flexible and group the icon and Remove action in a nonshrinking actions container.

## Add-form behavior

Keep the existing toggle component. Change its explanatory text because the current tooltip says `www.example.com` is controlled by the setting, which conflicts with enforcement. Use:

```text
Allow additional subdomains such as video.example.com. The main domain and www are always allowed.
```

When the form is submitted:

1. Normalize the entered website to a domain.
2. Read `#allow-subdomains.checked` as an actual boolean.
3. If the domain is new, add `{ domain, allowSubdomains }`.
4. If the domain already exists, update that rule's `allowSubdomains` value. Do not add a duplicate.
5. Sort by normalized domain.
6. Clear the address input.
7. Reset the add-form toggle to `false` so the next entry does not inherit the previous choice accidentally.
8. Render the desired state and save the full policy.

Adding an existing domain is therefore an edit. If its setting changes, save it; if it is identical, no service update is required. A small status such as `No changes to apply.` is optional, but the form should still clear successfully.

## Renderer state and operations

Replace the `websites` string array in `src/renderer.js` with one versioned object:

```js
let allowlist = { version: 2, websites: [] }
```

On load:

```js
const result = await window.carecare.getAllowedWebsites()
allowlist = result.allowlist
```

On save:

```js
const result = await window.carecare.saveAllowedWebsites(allowlist)
allowlist = result.allowlist
```

Render rows from `allowlist.websites`. Display `https://${rule.domain}` to preserve the current appearance, but use `rule.domain` as the stable identity for updates and removal.

Define small pure operations, preferably outside DOM event handlers:

```js
upsertRule(allowlist, domain, allowSubdomains)
setRuleSubdomains(allowlist, domain, allowSubdomains)
removeRule(allowlist, domain)
```

Each operation should create a new version 2 payload instead of mutating a rule object in place. This makes save snapshots predictable and simplifies testing.

The row icon click should:

1. Return immediately if `busy` is true.
2. Flip only the selected rule's `allowSubdomains` value.
3. Render the new desired state immediately.
4. Call the existing save/apply flow.

The Remove button should filter by `rule.domain`. It must not compare object identity.

## Busy and save behavior

The current `setBusy` implementation disables the text input, first form button, Retry button, and row buttons. Extend it to disable the form checkbox as well. Selecting only `form.querySelector('button')` is fragile; keep explicit references to the add button and add-form checkbox.

While saving:

- disable the address input, Add button, add-form toggle, every row icon, every Remove button, and Retry button;
- retain `Saving and applying…` in the status region;
- prevent a second row edit from racing with the in-flight snapshot.

The main process already serializes operations through `saveQueue`. UI disabling remains valuable because it prevents confusing intermediate states.

The service can return `applied: false` while local persistence succeeds. Continue displaying the service's exact message and retain the desired rule state so Retry resends it. An IPC exception should display `Could not save changes. Retry.` and retain the user's desired state in memory. Do not claim that Windows applied a setting unless `result.enforcement.applied` is true.

## HTML changes

In `src/index.html`:

1. Keep the existing form structure and switch.
2. Correct the tooltip so it explains that `www` is always included.
3. Optionally change the visible label to `Allow additional subdomains` for consistency with row tooltips.
4. Add no static row markup; rows remain generated by the renderer.

The list can keep `aria-live="polite"`, but toggling a row should also update the existing `#save-status`. Avoid announcing the entire rebuilt list by adding excessive live regions.

## CSS changes

In `src/styles.css`:

- add a `.website-label` class for the flexible, truncated domain text;
- add a `.website-actions` container using `display: flex`, centered alignment, a small gap, and `flex: 0 0 auto`;
- add `.subdomain-button` with a 36px minimum hit area, transparent background, borderless base style, and muted off state;
- style `[aria-pressed="true"]` with full-opacity connected icon details;
- style `:hover`, `:focus-visible`, and `:disabled` consistently with existing controls;
- reuse or generalize the existing tooltip styles for the row status tooltip;
- scope the current `li span` truncation rule to the domain label so SVG/tooltip spans are not accidentally truncated;
- at the existing narrow breakpoint, preserve the action group and allow the domain label to shrink.

The row height can remain close to 60px. Avoid adding a second line to every row unless usability testing shows that the icon and tooltip are insufficient.

## Preload and IPC contract

The existing method names can remain:

```js
getAllowedWebsites()
saveAllowedWebsites(allowlist)
```

Update the parameter name in `src/preload.cjs` from `websites` to `allowlist` for clarity. This is an internal naming change; it does not broaden the bridge or expose a new IPC channel.

The authoritative request and response shape should be:

```js
{
  version: 2,
  websites: [
    { domain: "example.com", allowSubdomains: true }
  ]
}
```

The response remains:

```js
{
  allowlist: {
    version: 2,
    websites: [
      { domain: "example.com", allowSubdomains: true }
    ]
  },
  enforcement: {
    applied: true,
    message: "Saved and applied by Windows service (browser proxy)."
  }
}
```

`result.websites`, the legacy display list, can remain for one compatibility release if other callers may rely on it. The renderer must stop reading it. Remove it and `fromLegacyEditor` only after confirming there are no older renderer bundles or other callers that use the legacy contract.

## Main-process changes

`src/main.js` already validates version 2 payloads through `normalizeAllowlist`, persists them, and passes them to the Windows service. For this UI change:

1. Keep accepting the complete version 2 payload from IPC.
2. Continue validating the entire payload in the trusted main process; renderer validation is only for user feedback.
3. Continue normalizing and deduplicating by domain before saving.
4. Return the normalized `allowlist` so the renderer always uses canonical domains and sort order.
5. Keep the save queue and distinction between local persistence and confirmed Windows enforcement.

Do not introduce a special “toggle one domain” IPC call. Sending the complete snapshot matches the service protocol, makes persistence atomic, and avoids a renderer/main-process state merge.

After the renderer has moved to rule objects, the legacy-array branch in `saveAndApply` is no longer used by the application. Keep it temporarily for migration compatibility or remove it in a later cleanup with an explicit compatibility decision.

## Rule-model changes

`src/allowlist.js` already provides the authoritative validation and normalization. Add pure renderer-facing operations there or in a new `src/allowlist-editor.js` module so they can be tested without Electron or a browser DOM.

Recommended invariants:

- input domains always pass through the existing hostname normalization;
- `allowSubdomains` must be `true` or `false`, never a truthy value;
- one normalized domain has one rule;
- adding an existing domain replaces its setting;
- changing one row preserves every other rule exactly;
- the returned collection remains sorted;
- version remains exactly `2`;
- 500 submitted user rules remain the limit.

## Automated validation

Add unit tests for the pure editor operations:

1. Adding a new domain stores the checkbox boolean.
2. Adding `www.example.com` updates the existing `example.com` rule.
3. Adding HTTP/HTTPS/path/port variants never creates duplicates.
4. Adding an existing domain changes only its setting.
5. Clicking a row icon changes only that domain.
6. Removing a rule compares normalized domains rather than object identity.
7. Sorting is stable by domain.
8. A missing, string, number, or null boolean is rejected.
9. The 500-rule limit remains enforced.
10. Form reset returns the add toggle to off.

Add renderer integration coverage with a minimal DOM test harness or extracted controller functions:

- loading uses `result.allowlist`, including a mix of enabled and disabled rows;
- each icon has the correct `aria-pressed`, label, tooltip, and visual class;
- icon activation sends the full version 2 payload;
- controls are disabled for the full save duration;
- a successful response replaces state with the normalized returned payload;
- service rejection retains the desired policy and displays the returned message;
- IPC failure leaves Retry available;
- repeated rapid activation cannot enqueue conflicting UI edits while busy.

Keep the existing transport tests and update any fixtures that still treat the renderer request as a string array.

## Manual UI and Windows acceptance

On Windows, after the automated suite passes:

1. Add a controlled domain with the form toggle off. Confirm its row icon shows off, the main/`www` hosts work, and child hosts are blocked.
2. Click the row icon. Confirm it changes to on, the status reports saving/application, and child and nested hosts work.
3. Click it off during an active child-domain HTTP download and HTTPS tunnel. Confirm the icon and saved policy show off and both connections are revoked.
4. Add an explicit child rule, then disable its parent's setting. Confirm the explicit child remains allowed.
5. Add the same domain through `www`, HTTP, HTTPS, a path, a port and different case. Confirm one row remains and the form's chosen setting updates it.
6. Restart Electron, the service, and Windows. Confirm every row icon reconstructs from persisted booleans.
7. Simulate a stopped/incompatible service. Confirm the icon reflects the locally desired state, the status clearly says enforcement was not confirmed, and Retry resends the same version 2 payload.
8. Navigate every control by keyboard. Confirm Space/Enter toggles the row icon, focus remains visible, tooltips do not trap focus, and disabled controls cannot change state.
9. Inspect with a screen reader. Confirm each row announces its domain, whether additional subdomains are allowed, and that the icon is a pressed/unpressed button.
10. Resize to the minimum supported width. Confirm long IDN/Punycode domains truncate without hiding or shrinking the row icon and Remove action.

## Recommended implementation order

1. Add/test pure rule editing operations.
2. Move renderer state and saves to the version 2 payload.
3. Read/reset the existing add-form toggle.
4. Render the row icon buttons and implement per-row updates.
5. Correct explanatory copy and add responsive/accessibility styling.
6. Add renderer/IPC tests.
7. Run JavaScript, .NET and Windows browser-policy tests.
8. Perform the Windows UI acceptance sequence above before enabling the feature in a release.
